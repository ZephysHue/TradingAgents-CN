# 多热度层级市场机制发现 v1

**状态：设计冻结候选（design_only）**  
**数据源：Bybit V5 USDT 线性永续合约**  
**目标：发现跨标的、跨热度层级、跨周期稳定的可检验市场机制；本阶段不产生交易策略。**

## 1. 结论与边界

既有 V1、V2、V3 已被各自成本后收益、回撤和稳定性证据拒绝；最近一次冻结 V1 信号在六个 Bybit 标的、15 分钟级、Scenario D 下亦全部为负期望。这只能否定这些既有规则，不能推出“加密市场不存在可交易机制”。

本设计不继续优化 V1，也不立刻编写 V4。先扩大**研究宇宙**，检验可预测关系是否能在热门、中度热门、低热门标的之间复现。

禁止事项：

- 不运行 Entry/Exit、SL/TP、仓位、PnL、资金曲线或参数搜索。
- 不因开发集结果修改特征、分层边界、目标 Horizon 或入选门槛。
- Holdout 只读取冻结后的候选注册表，不新增候选。

## 2. 市场宇宙与防前视分层

### 2.1 合约资格

每次调仓时点仅从 Bybit `USDT` 结算、`LinearPerpetual`、状态为 `Trading` 的合约中选择。所有时间戳均为 UTC；未收盘 K 线、停牌/缺失区间和不完整历史不得参与。

### 2.2 滚动热度分层

每月第一根完整 UTC 日线完成后重建一次宇宙。第 `m` 月的层级只使用严格早于该时点的 30 个自然日数据，并在该月内锁定；不得用本月或未来成交额决定归类。

基础热度指标为 30 日累计报价成交额：

```text
turnover_30d(symbol, m) = sum(15m K 线 turnover，过去 30 个完整自然日)
```

准入数据质量条件：过去 30 日 15 分钟 K 线覆盖率不少于 99%，成交额为正，且不存在超过 4 根连续缺失 bar。符合条件的合约按 `turnover_30d` 降序排序：

| 层级 | 固定排名带 | 含义 |
|---|---:|---|
| hot | 1–10 | 热门、高流动性 |
| mid | 45–55 百分位（端点向内取整） | 中度热门 |
| low | 75–85 百分位（端点向内取整） | 低热门但通过质量门槛 |

若某一层不足 5 个合约，则该月该层标记为 `insufficient_universe`，不以其他层补齐，也不外推结果。首次实施先进行不含未来收益标签的数据普查，生成并冻结 `universe_registry.json` 与 SHA256；预测性检验只能读取该注册表。

## 3. 数据、周期与目标

### 3.1 周期

研究周期固定为 `5m`、`15m`、`1h`、`4h`。5 分钟数据直接下载；15 分钟、1 小时、4 小时数据使用各自的完整已收盘 K 线，不跨时区混合重采样。

Bybit K 线提供 OHLCV 与 turnover。历史 taker volume、trade count、资金费率、历史持仓量未在本 v1 中假设可得，因此不填充、不代理、不作为特征。

### 3.2 无交易目标

所有目标均为未来对数收益：

```text
r(t, h) = log(close[t + h] / close[t])
```

| 输入周期 | 短 Horizon | 中 Horizon |
|---|---:|---:|
| 5m | 1h（12 bar） | 4h（48 bar） |
| 15m | 1h（4 bar） | 4h（16 bar） |
| 1h | 4h（4 bar） | 1d（24 bar） |
| 4h | 1d（6 bar） | 3d（18 bar） |

目标仅用于条件分布、五分位差异、秩相关和稳定性检验，不转换为订单或收益曲线。

## 4. 固定特征库

每个特征采用仅截至 bar `t` 的数据计算。v1 特征族固定如下：

1. **趋势/路径效率**：过去收益、累计方向性、效率比率。
2. **波动状态**：ATR 比率、实现波动率、当期与滚动区间比率。
3. **成交额状态**：turnover 相对滚动中位数、turnover z-score、价格波动与成交额的联合状态。
4. **区间位置**：收盘相对过去高低区间的位置、距离滚动高低点的标准化距离。
5. **横截面状态**：同一时间点、同层级内的相对收益和相对波动分位。

特征目录、窗口和公式在运行前写入 `feature_catalog.json` 并与宇宙注册表共同冻结。不得在开发集看过标签后新增或删除特征。

## 5. 开发/验证与候选门槛

### 5.1 时间切分

- Development：截至 `2024-12-31 23:59:59 UTC`。
- Holdout：`2025-01-01 00:00:00 UTC` 起。
- 新上线合约仅在拥有完整 30 日回看并通过质量门槛后进入对应月份；不补写其上线前历史。

Development 按自然季度形成独立折。每一个 `(feature, timeframe, horizon, tier)` 在各折内独立计算，不跨 Development/Holdout 拟合、标准化或排序。

### 5.2 成本基线

本阶段不产生交易结论，但候选必须超过分层执行成本底线。先执行不含未来收益标签的流动性普查，为 hot/mid/low 分别冻结 `cost_floor_registry.json`：

```text
edge_floor[tier] = round_trip_fee[tier] + 2 * one_way_slippage[tier]
```

费用与滑点来源、数值、版本和 SHA256 必须记录。未冻结成本注册表时，不得产生“可交易候选”的措辞。

### 5.3 Development 入选

对特征五分位的条件均值，定义：

```text
effect = mean(r | feature in Q5) - mean(r | feature in Q1)
```

某关系进入 Candidate Registry 必须同时满足：

1. 在至少 2 个热度层级中，季度折的 effect 方向一致；
2. 在每个满足条件的层级，跨折中位 `abs(effect)` 严格大于该层 `edge_floor`；
3. Spearman 相关在同一方向，且经 Benjamini-Hochberg FDR 校正后 `q <= 0.10`；
4. 不得由单一标的贡献：满足条件层级中，至少 60% 的合约具有同方向 effect；
5. 记录完整特征、周期、Horizon、层级、折别、统计量及方向，冻结 `candidate_registry.json` 和 SHA256。

候选数为 0 是有效终止结果：不创建策略，不调低门槛。

### 5.4 Holdout 验证

Holdout 只读取 Candidate Registry；特征、层级、Horizon、成本底线和方向均不可修改。候选通过 Holdout 需同时满足：

1. 至少 2 个层级保持冻结方向；
2. 每个通过层级的合约等权中位 effect 超过其冻结成本底线；
3. 按月份分块 bootstrap 的 95% 置信区间下界大于 0；
4. 不存在任一层级的系统性反向（超过 60% 合约反向）。

通过只表示“市场机制候选得到样本外支持”，仍不表示交易策略可用。

## 6. 数据质量与可审计工件

每次实施至少输出：

| 工件 | 必含内容 |
|---|---|
| `universe_registry.json` + `.sha256` | 月份、层级、排名、30 日成交额、入选/排除原因 |
| `data_manifest.json` | 合约、周期、UTC 范围、行数、数据哈希、下载时间 |
| `data_quality.csv` | 覆盖率、连续缺口、不可用原因 |
| `feature_catalog.json` | 公式、窗口、版本、哈希 |
| `cost_floor_registry.json` + `.sha256` | 各层费用、滑点、成本底线、来源 |
| `development_univariate.csv` | 特征-层级-周期-Horizon-季度统计量 |
| `candidate_registry.json` + `.sha256` | 冻结候选；空数组也必须生成 |
| `holdout_candidate_validation.csv` | 仅冻结候选的验证结果 |
| `MULTITIER_MECHANISM_DISCOVERY_V1.md` | 方法、边界、结论和停止/推进决定 |

## 7. 推进门闩

只有至少一个候选同时通过 Development 与 Holdout 后，才能另行起草**策略转换设计**。该设计必须单独规定：信号到订单的映射、持有期、成本、滑点、资金费率、流动性约束、仓位、止损止盈、walk-forward 与基准比较；未经独立评审不得实现。

若没有候选，本阶段结论应为“已检验的多层级机制库未发现足以覆盖对应成本的稳定关系”，而不是“所有加密策略均不可用”。

## 8. 实施验收标准

1. 任一月份的层级证明只使用此前 30 日数据，抽样审计不得发现未来数据泄漏。
2. 每个层级、周期、Horizon 的数据质量工件可复算，缺口不被静默填补。
3. Development 和 Holdout 的候选注册表哈希一致；Holdout 不新增行。
4. 所有候选门槛可由 CSV/JSON 逐项复算；候选数为 0 也视为完整交付。
5. 本阶段运行日志不得包含订单、成交、PnL、资金曲线、SL/TP 或仓位优化结果。

## 9. 当前下一步

先做一次**无标签数据普查**，仅验证 Bybit 历史可用性、各月层级样本数、K 线覆盖率与成本底线资料是否足以冻结注册表。普查通过后，再实施 Development 机制检验；不得跳过注册表冻结直接研究收益标签。
